Live UI testing with Playwright

SF-SDLC ships the Playwright MCP server as sf-browser. The QA agent opens a real browser on your sandbox, clicks through the test case, checks what a user would see, such as whether a Lightning Web Component renders correctly on the Account page, and saves a screenshot as evidence. When the screenshot shows a problem, it becomes a defect, the fix is deployed to the sandbox, and the same check runs again.

How a UI test runs

Claude starts the browser

When the QA agent needs a UI case, Claude Code starts sf-browser (@playwright/mcp, pinned, fetched by npx). It uses Google Chrome, or Chrome for Testing when Chrome is missing. Nothing to install beyond Node.js.

You sign in once

The first time, the browser shows the Salesforce login page and you sign in yourself. The session is kept in .sf-sdlc/browser-profile/, so later sessions and laptop restarts reuse it until Salesforce's own timeout. Claude never sees or types a password.

The agent follows the test case

It navigates, reads the page's accessibility snapshot, clicks and types only what the case says, and checks each expected result.

Evidence and defects

One screenshot per verified expected result goes to test-runs/evidence/<TR-id>/. A failure becomes a DEF-nnn with steps, expected and actual results and the screenshot; /sf-sdlc:retest re-runs it after the fix.

Sandboxes only. sf-sdlc browser url returns an address only for sandbox, scratch and developer orgs, never a session link. The pre-mcp hook asks before the browser opens a production-class or unclassified org, session IDs and OAuth codes are redacted from what the browser returns, and the browser profile is blocked from Claude's file tools.

Commands: sf-sdlc browser status (ready, and where the sign-in is kept), sf-sdlc browser url --org uat, sf-sdlc browser reset (sign out everywhere). Settings: browser.enabled, browser.browser (chrome, msedge, chromium, firefox, webkit), browser.headless.
