Getting started

Salesforce SDLC plugin for Claude Code

One plugin that takes a Salesforce project from meeting transcripts to a production release: grounding in your business and org, BRD, Jira stories, architecture, spec-driven build, code review, validated deployment, testing, re-test, release and observation, with Salesforce Hosted MCP Servers for org context and guard hooks around every org-changing command.

0SetupGGround1BRD2Stories3Architecture4Spec & plan5Build6Review7Deploy8Test9Re-test10Release11Observe
10agents, one per stage
22slash commands
11SDLC method skills
176Salesforce skills, installed on demand
7hook events guarded
4Salesforce Hosted MCP servers, signed in through the sf CLI
3 · 2 · 2workflows · monitors · output styles

Hosted MCP Servers are required. They give the agents just the org context they need. See how your coding agent connects to them, and which to turn on.

Every stage writes a draft and stops. A person reviews it and fills in its approval record before the next stage starts. Agents never approve their own work.

Install

Pick one form per project. Using both makes every agent and command appear twice.

⬇ Download the plugin (.zip) ⬇ Download the .claude folder (.zip) 

/plugin marketplace add nagarroARBsf/Sf-skills-agents
/plugin install sf-sdlc@nagarro-sf
/sf-sdlc:setup

Commands are namespaced /sf-sdlc:<name>. The CLI is on the PATH as sf-sdlc. Try a local checkout with claude --plugin-dir plugins/sf-sdlc.

# from the root of your Salesforce DX project
cp -r /path/to/Sf-skills-agents/.claude ./.claude
claude
/sdlc-setup

Lifecycle commands are /sdlc-<name> and build-phase commands are /sdd-<name>. The CLI is node .claude/bin/sf-sdlc.

Quickstart

Run setup in your Salesforce project

Checks tools, writes .claude/sf-sdlc.json, records what already exists and recommends only the skills the project needs.

/sf-sdlc:setup

Turn on the Salesforce Hosted MCP Servers

Required. In the org: Setup → MCP Servers → turn on Metadata Grounding, Metadata Experts and the servers your project needs. Then log in once with the Salesforce CLI and check the connection.

sf org login web --alias my-dev
sf-sdlc mcp status

Tell it which orgs are production

Open .claude/sf-sdlc.json and list every production alias in orgs.production. This is the one setting you must get right.

"orgs": { "dev": "orion-dev", "qa": "orion-qa", "uat": "orion-uat", "production": ["orion-prod"] }

Start at the stage you are in

Transcripts? Start with the BRD. A story already in Jira? Start with the spec.

/sf-sdlc:brd docs/sdlc/00-inputs/
/sf-sdlc:specify US-04-02
/sf-sdlc:trace        # where are we, what is blocked

What goes in the plugin

The sf-sdlc plugin has one of nearly every kind of Claude Code plugin component. Select a file or folder to read what it is for, what you configure, and how you use it. Switch to Your project to see what setup creates in your Salesforce repository.

      How the pieces work together

      A command names an agent; the agent loads its method skills and any Salesforce skills installed in the project; real work on Salesforce goes through the sf-sdlc CLI and the sf CLI, and org context (what metadata already exists, metadata schemas) comes from Salesforce Hosted MCP Servers. Hooks sit around every tool call.

      CommandYou type /sf-sdlc:review US-04-02
      Agentsdlc-code-review-agent, read-only tools
      Skillssdlc-code-review, sdlc-workflow + installed Apex skills
      CLIsf-sdlc analyze, delta → sf code-analyzer
      Draftspecs/US-04-02-…/review.md with a verdict, then stop
      Hooks around every step: SessionStart prints project facts and instructions · PreToolUse runs the production-org, secret, branch, commit and hosted-MCP guards · PostToolUse runs source checks and writes the audit log · PostToolUseFailure explains deploy failures · Stop checks task evidence. Monitors report when a background deploy or test run changes state.

      Plugin vs. copy-in folder

      Configuration

      What you need to provide

      The plugin ships no project-specific values. Everything that differs between projects (org aliases, branches, Jira keys, thresholds, paths) comes from files in your repository. sf-sdlc init creates them; setup never overwrites an existing file.

      File in your projectCommit?What you set
      .claude/sf-sdlc.jsonYesOrg aliases and which are production, branch rules, Jira project, coverage target, promotion order, document paths, hook mode
      .claude/sf-sdlc.local.jsonNoPersonal overrides, same shape; for example your own scratch org
      .claude/settings.jsonYesClaude Code permissions (allow / ask / deny). Plugin users get a template from templates/project-settings.json
      code-analyzer.ymlYesWhich Code Analyzer rules run and at what severity, plus custom rules (ships NoHardcodedSalesforceIds)
      .github/workflows/sf-code-analyzer.ymlYesCode Analyzer on the files changed in each pull request; keep its threshold equal to the local one
      docs/sdlc/00-grounding/Yesontology.yaml (business terms → Salesforce objects) and feature-map.md (components per feature), drafted by setup
      .claude/sf-sdlc.skills.lock.jsonYesNothing by hand: records installed skills so skills sync never overwrites your edits
      specs/constitution.mdYesCreated by /sf-sdlc:constitution: your engineering principles, trigger framework, logging utility

      Project config keys that matter most

      KeyWhy it matters
      orgs.productionEvery alias listed here is treated as production regardless of what the org looks like. An org that cannot be classified is never treated as safe.
      git.protectedBranchesBranches agents may not push to; force-pushes to them are always blocked.
      jira.projectKey, jira.fields.*Where the story agent creates issues, and your custom field IDs (story points, acceptance criteria).
      quality.coverageTarget, analyzerSeverityThresholdPer-class Apex coverage target and the Code Analyzer severity that blocks a commit (1 Critical … 5 Info).
      deploy.pipeline, deploy.testLevelPromotion order and test level per stage. Production may not be NoTestRun.
      mcp.servers, mcp.orgWhich Salesforce Hosted MCP Servers the agents may use, and the org (role or alias) they sign in to. Headless 360 and Data 360 are off by default.
      hooks.modeobserve reports what would be blocked; enforce blocks. Start in observe for a week. The production and secret guards enforce in every mode.

      Every key, with examples: SETUP.md.

      Salesforce Hosted MCP Servers Required

      Hosted MCP servers are how the agents see your org: what metadata already exists, the exact schema of each type, and live Setup and data. Without them an agent guesses names and duplicates what is already there. Setting them up is a required step, not an extra. Which servers you turn on depends on the project; the ones marked Required are needed by every project.

      Which servers your project needs

      Standard servers are off by default; an administrator turns each one on. Every tool call runs as the signed-in user, so field-level security, object permissions and sharing rules always apply. Full list: Standard MCP Servers Reference.

      ServerTurn it on whenHow this kit connects
      Metadata Grounding (Beta) RequiredEvery project. Agents find existing objects, fields, flows, Apex, LWC and permission sets by meaning before proposing new ones. Read-only.       Set them up

      Turn the servers on in the org

      Setup → Quick Find MCP Servers → MCP Servers under API Catalog. Turn on the required servers and the ones your project needs. Allow two minutes.

      Connect the kit's servers with the Salesforce CLI login

      No client ID or secret: sf-mcp-proxy gets a short-lived token from the org through your CLI login. List the servers in mcp.servers and, if needed, the org in mcp.org.

      sf org login web --alias my-dev
sf-sdlc mcp status

      Connect the other servers through an External Client App

      Setup → External Client App Manager → New. Enable OAuth, add the scopes mcp_api and refresh_token, require PKCE, select Issue JSON Web Token (JWT)-based access tokens for named users, and add your client's callback URL (Claude Code: http://localhost:<port>/callback). A new app can take up to 30 minutes to work. Use the server name shown in Setup:

      claude mcp add --transport http --scope project \
  --client-id <consumer key> --callback-port <port> \
  sf-crm-analytics https://api.salesforce.com/platform/mcp/v1/<server name>
# sandbox or scratch org: .../platform/mcp/v1/sandbox/<server name>

      Then /mcp → authenticate in the browser. Cursor, Codex and GitHub Copilot use the same server URL and consumer key.

      Restart and check

      Restart Claude Code. /mcp lists every server; a kit server that is not enabled or not turned on in the org shows no tools instead of failing to start.

      Secure them

      ControlWhat to set
      Who can connectIn the ECA's OAuth Policies, require a custom permission set for pre-authorization and assign it only to approved users. Profiles can restrict access the same way.
      Where they connect fromRestrict the ECA to known IP ranges when your MCP client uses stable addresses. Check with the client vendor first; some use more ranges than the allowlist holds.
      How long access lastsRefresh token validity 30 days or less, with refresh token rotation. Turn on single logout so ending a Salesforce session ends the MCP session.
      Client secretRequire it only for web-based clients; desktop and CLI clients use PKCE.
      What tools can reachField-level security, object permissions and sharing rules apply to every call. Start with read-only servers; add write servers per project. In this kit, Headless 360 dispatch and Data 360 execute always ask first, naming the org.
      What happenedEvery call is logged and attributed to a named user. Review the logs alongside the kit's local audit log.

      Per-user options

      Declared under userConfig in plugin.json. Each developer sets them for themselves with /plugin configure sf-sdlc@nagarro-sf.

      OptionValuesEffect
      Hook modeproject (default), observe, enforce, offOverrides hooks.mode for you only
      Audit logon (default) / offTurns the local audit log off for you

      Jira: the plugin's .mcp.json connects the Atlassian remote MCP server. Sign in once with /mcp. Without it, the story agent writes a Jira CSV you can import. Salesforce: see Salesforce Hosted MCP Servers.

      Traceability runs through one ID chain: BR-04 → FR-04.2 → US-04-02 → LLD-US-04-02 → TC-US-04-02-007 → TR-… → DEF-012 → DEP-005 → REL-1.4.0. /sf-sdlc:trace shows it at any time.

      Every repeated mistake becomes a constraint. Instructions and skills are advisory; tests, Code Analyzer rules, hooks and quality gates are deterministic. A defect closes only when its record names the constraint added (or says why none fits), and the reviewer recommends the strongest check that would have caught a finding.

      /sf-sdlc:setup                          # once per project
/sf-sdlc:brd docs/sdlc/00-inputs/       # transcripts in, BRD draft out      → BA reviews and signs

/sf-sdlc:diagram solution US-04-02      # what is new, changed, unchanged
/sf-sdlc:specify US-04-02               # then clarify → plan → tasks, each reviewed
/sf-sdlc:implement                      # tests first, task by task
/sf-sdlc:verify                         # evidence for each acceptance criterion
/sf-sdlc:review US-04-02                # independent review + Code Analyzer
/sf-sdlc:deploy qa                      # validate, then quick deploy
/sf-sdlc:test-run qa US-04-02           # run tests, coverage, log defects
/sf-sdlc:retest DEF-012                 # after the fix
/sf-sdlc:deploy production              # only when you name it; asks again
/sf-sdlc:release 1.4.0                  # readiness, notes, close-out

      By role

      Business analyst / manager

      No Salesforce CLI or org needed.

      • brd, stories, test-cases, trace
      • /output-style → Salesforce Delivery Lead for plain English
      • Jira CSV when Jira is not connected

      Developer / architect

      Spec first, tests first.

      • specify → plan → tasks → implement → verify
      • /output-style → Salesforce Engineer for terse, evidence-led answers
      • sf-sdlc check and analyze before committing

      Release engineer / QA

      Validate before deploying.

      • deploy <org> and release can only be started by a person
      • test-run, retest; monitors report job completion
      • Workflow sdlc-release-readiness gathers evidence in parallel

      Skills on demand

      No Salesforce technical skill is loaded by default, because every loaded skill costs context in every session. The 176 skills sit in skill-library/. Setup reads your project and recommends a small set with the evidence for each; only the ones you confirm are copied into your project's .claude/skills/.

      sf-sdlc skills recommend                 # evidence-based, from your metadata folders
sf-sdlc skills recommend --profile admin # starter sets: developer, admin, ba
sf-sdlc skills install platform-apex-generate platform-apex-test-run
sf-sdlc skills sync --dry-run            # after an upgrade; never overwrites a skill you edited

      Or simply run /sf-sdlc:skills.

      Safety

      Guards and hooks

      GuardWhat it doesCan be relaxed?
      Production-org guardClassifies the target of every org-changing sf command. Production: denies NoTestRun and direct deploys, asks for everything else. Unknown orgs also ask.Policy only; on in every mode
      Secret guardBlocks writing or committing auth URLs, private keys, tokens and anything in .sf/ or .sfdx/No
      Branch guardBlocks pushes to protected branches; force-pushes always blockedhooks.mode
      Commit gateRuns the official Code Analyzer (Recommended plus your custom rules) on the files being committed; the CI workflow does the same for pull requestshooks.mode
      Hosted MCP guardHeadless 360 dispatch and Data 360 execute can change the org: they always ask, naming the org and its class, even when the tool is allow-listedNo
      Source checkAfter each edit: SOQL/DML in loops, missing sharing, hard-coded IDs, SeeAllDataAdvisory
      Audit logWho ran which org-affecting command against which org, in .sf-sdlc/audit.jsonlhooks.auditLog
      Person-only commandsdeploy and release carry disable-model-invocation: trueNo

      Hooks and permission rules steer an agent; they are not a security boundary. Keep org permissions, branch protection and CI in place.

      Known limitations

      • Not yet run end to end against a real org or Jira project. Prove deploy, test-run and Jira paths in a sandbox first.
      • No behavioural evaluation suite yet; agent quality is unmeasured.
      • Monitors and themes are experimental in Claude Code; monitors do not run in headless sessions.
      • Hosted MCP servers are reached through Salesforce's Beta v1-beta.2 route, as Salesforce's own plugin does; it may change. Grounding results can lag recent changes and are never a complete list.
      • Source checks are heuristics; the Code Analyzer is the authoritative scan.

      The full list is in the README.

      Maintaining the kit

      Edit .claude/, never the generated folders in plugins/sf-sdlc/. Then regenerate and check:

      python3 scripts/build-claude-plugin.py          # regenerate the plugin and the skill catalog
python3 scripts/build-claude-plugin.py --check  # fail if anything generated is stale
node --test tests/kit.test.js                   # hook and CLI unit tests
claude plugin validate plugins/sf-sdlc --strict

      Bump version in plugins/sf-sdlc/.claude-plugin/plugin.json on every release, or installed copies will not update.
