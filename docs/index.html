Getting started

Salesforce SDLC plugin for Claude Code

One plugin that takes a Salesforce project from meeting transcripts to a production release: BRD, Jira stories, architecture, spec-driven build, code review, validated deployment, testing, re-test and release, with guard hooks around every org-changing command.

0Setup1BRD2Stories3Architecture4Spec & plan5Build6Review7Deploy8Test9Re-test10Release
10agents, one per stage
22slash commands
11SDLC method skills
174Salesforce skills, installed on demand
7hook events guarded
3 · 2 · 2workflows · monitors · output styles

Every stage writes a draft and stops. A person reviews it and fills in its approval record before the next stage starts. Agents never approve their own work.

Install

Pick one form per project. Using both makes every agent and command appear twice.

⬇ Download the plugin (.zip) ⬇ Download the .claude folder (.zip) 

/plugin marketplace add nagarroARBsf/Sf-skills-agents
/plugin install sf-sdlc@nagarro-sf
/sf-sdlc:setup

Commands are namespaced /sf-sdlc:<name>. The CLI is on the PATH as sf-sdlc. Try a local checkout with claude --plugin-dir plugins/sf-sdlc.

# from the root of your Salesforce DX project
cp -r /path/to/Sf-skills-agents/.claude ./.claude
claude
/sdlc-setup

Lifecycle commands are /sdlc-<name> and build-phase commands are /sdd-<name>. The CLI is node .claude/bin/sf-sdlc.

Quickstart

Run setup in your Salesforce project

Checks tools, writes .claude/sf-sdlc.json, records what already exists and recommends only the skills the project needs.

/sf-sdlc:setup

Tell it which orgs are production

Open .claude/sf-sdlc.json and list every production alias in orgs.production. This is the one setting you must get right.

"orgs": { "dev": "orion-dev", "qa": "orion-qa", "uat": "orion-uat", "production": ["orion-prod"] }

Start at the stage you are in

Transcripts? Start with the BRD. A story already in Jira? Start with the spec.

/sf-sdlc:brd docs/sdlc/00-inputs/
/sf-sdlc:specify US-04-02
/sf-sdlc:trace        # where are we, what is blocked
Plugin structure

What goes in the plugin

The sf-sdlc plugin has one of nearly every kind of Claude Code plugin component. Select a file or folder to read what it is for, what you configure, and how you use it. Switch to Your project to see what setup creates in your Salesforce repository.

      How the pieces work together

      A command names an agent; the agent loads its method skills and any Salesforce skills installed in the project; real work on Salesforce goes through the sf-sdlc CLI and the sf CLI. Hooks sit around every tool call.

      CommandYou type /sf-sdlc:review US-04-02
      Agentsdlc-code-review-agent, read-only tools
      Skillssdlc-code-review, sdlc-workflow + installed Apex skills
      CLIsf-sdlc analyze, delta → sf code-analyzer
      Draftspecs/US-04-02-…/review.md with a verdict, then stop
      Hooks around every step: SessionStart prints project facts and instructions · PreToolUse runs the production-org, secret, branch and commit guards · PostToolUse runs source checks and writes the audit log · PostToolUseFailure explains deploy failures · Stop checks task evidence. Monitors report when a background deploy or test run changes state.

      Plugin vs. copy-in folder

      .claude/ in this repository is the single source of truth. plugins/sf-sdlc/ is generated from it by python3 scripts/build-claude-plugin.py, which rewrites paths and command names on the way.

      ComponentCopy-in .claude/Plugin plugins/sf-sdlc/
      Agents, commands, SDLC skills, skill libraryYesYes
      Command names/sdlc-brd, /sdd-plan/sf-sdlc:brd, /sf-sdlc:plan
      HooksIn settings.jsonhooks/hooks.json
      CLInode .claude/bin/sf-sdlcsf-sdlc on the PATH
      Project instructions and coding rulesCLAUDE.md, rules/Printed at session start; rules become the salesforce-coding-rules skill
      Monitors, themes, Jira MCP, per-user optionsNo (plugin-only features)Yes
      Configuration

      What you need to provide

      The plugin ships no project-specific values. Everything that differs between projects (org aliases, branches, Jira keys, thresholds, paths) comes from files in your repository. sf-sdlc init creates them; setup never overwrites an existing file.

      File in your projectCommit?What you set
      .claude/sf-sdlc.jsonYesOrg aliases and which are production, branch rules, Jira project, coverage target, promotion order, document paths, hook mode
      .claude/sf-sdlc.local.jsonNoPersonal overrides, same shape; for example your own scratch org
      .claude/settings.jsonYesClaude Code permissions (allow / ask / deny). Plugin users get a template from templates/project-settings.json
      code-analyzer.ymlYesWhich Code Analyzer rules run and at what severity
      .claude/sf-sdlc.skills.lock.jsonYesNothing by hand: records installed skills so skills sync never overwrites your edits
      specs/constitution.mdYesCreated by /sf-sdlc:constitution: your engineering principles, trigger framework, logging utility

      {
  "project":  { "name": "Orion Sales Cloud", "code": "ORION" },
  "orgs":     { "dev": "orion-dev", "qa": "orion-qa", "uat": "orion-uat",
                "devHub": "orion-hub", "production": ["orion-prod"] },
  "git":      { "mainBranch": "main", "integrationBranch": "develop",
                "protectedBranches": ["main", "develop", "release/*"],
                "branchPattern": "feature/{ticket}-{slug}" },
  "jira":     { "enabled": true, "site": "https://acme.atlassian.net", "projectKey": "ORION" },
  "quality":  { "coverageTarget": 85, "analyzerSeverityThreshold": 2, "bulkTestSize": 200 },
  "deploy":   { "pipeline": ["dev", "qa", "uat", "production"],
                "testLevel": { "qa": "RunLocalTests", "production": "RunLocalTests" },
                "validateBeforeDeploy": true, "allowDirectProductionDeploy": false, "useDelta": true },
  "paths":    { "docs": "docs/sdlc", "specs": "specs" },
  "hooks":    { "mode": "observe", "auditLog": true }
}

      Project config keys that matter most

      KeyWhy it matters
      orgs.productionEvery alias listed here is treated as production regardless of what the org looks like. An org that cannot be classified is never treated as safe.
      git.protectedBranchesBranches agents may not push to; force-pushes to them are always blocked.
      jira.projectKey, jira.fields.*Where the story agent creates issues, and your custom field IDs (story points, acceptance criteria).
      quality.coverageTarget, analyzerSeverityThresholdPer-class Apex coverage target and the Code Analyzer severity that blocks a commit (1 Critical … 5 Info).
      deploy.pipeline, deploy.testLevelPromotion order and test level per stage. Production may not be NoTestRun.
      hooks.modeobserve reports what would be blocked; enforce blocks. Start in observe for a week. The production and secret guards enforce in every mode.

      Every key, with examples: SETUP.md.

      Per-user options

      Declared under userConfig in plugin.json. Each developer sets them for themselves with /plugin configure sf-sdlc@nagarro-sf.

      OptionValuesEffect
      Hook modeproject (default), observe, enforce, offOverrides hooks.mode for you only
      Audit logon (default) / offTurns the local audit log off for you

      Jira: the plugin's .mcp.json connects the Atlassian remote MCP server. Sign in once with /mcp. Without it, the story agent writes a Jira CSV you can import.

      Walk-through

      /sf-sdlc:setup                          # once per project
/sf-sdlc:brd docs/sdlc/00-inputs/       # transcripts in, BRD draft out      → BA reviews and signs
/sf-sdlc:stories                        # backlog and Jira CSV               → PO reviews; "yes" creates issues
/sf-sdlc:architecture                   # HLD; then /sf-sdlc:architecture US-04-02 for the LLD
/sf-sdlc:diagram solution US-04-02      # what is new, changed, unchanged
/sf-sdlc:specify US-04-02               # then clarify → plan → tasks, each reviewed
/sf-sdlc:implement                      # tests first, task by task
/sf-sdlc:verify                         # evidence for each acceptance criterion
/sf-sdlc:review US-04-02                # independent review + Code Analyzer
/sf-sdlc:deploy qa                      # validate, then quick deploy
/sf-sdlc:test-run qa US-04-02           # run tests, coverage, log defects
/sf-sdlc:retest DEF-012                 # after the fix
/sf-sdlc:deploy production              # only when you name it; asks again
/sf-sdlc:release 1.4.0                  # readiness, notes, close-out

      By role

      Business analyst / manager

      No Salesforce CLI or org needed.

      • brd, stories, test-cases, trace
      • /output-style → Salesforce Delivery Lead for plain English
      • Jira CSV when Jira is not connected

      Developer / architect

      Spec first, tests first.

      • specify → plan → tasks → implement → verify
      • /output-style → Salesforce Engineer for terse, evidence-led answers
      • sf-sdlc check and analyze before committing

      Release engineer / QA

      Validate before deploying.

      • deploy <org> and release can only be started by a person
      • test-run, retest; monitors report job completion
      • Workflow sdlc-release-readiness gathers evidence in parallel

      Skills on demand

      No Salesforce technical skill is loaded by default, because every loaded skill costs context in every session. The 174 skills sit in skill-library/. Setup reads your project and recommends a small set with the evidence for each; only the ones you confirm are copied into your project's .claude/skills/.

      sf-sdlc skills recommend                 # evidence-based, from your metadata folders
sf-sdlc skills recommend --profile admin # starter sets: developer, admin, ba
sf-sdlc skills install platform-apex-generate platform-apex-test-run
sf-sdlc skills sync --dry-run            # after an upgrade; never overwrites a skill you edited

      Or simply run /sf-sdlc:skills.

      Safety

      Guards and hooks

      GuardWhat it doesCan be relaxed?
      Production-org guardClassifies the target of every org-changing sf command. Production: denies NoTestRun and direct deploys, asks for everything else. Unknown orgs also ask.Policy only; on in every mode
      Secret guardBlocks writing or committing auth URLs, private keys, tokens and anything in .sf/ or .sfdx/No
      Branch guardBlocks pushes to protected branches; force-pushes always blockedhooks.mode
      Commit gateRuns the official Code Analyzer on the files being committedhooks.mode
      Source checkAfter each edit: SOQL/DML in loops, missing sharing, hard-coded IDs, SeeAllDataAdvisory
      Audit logWho ran which org-affecting command against which org, in .sf-sdlc/audit.jsonlhooks.auditLog
      Person-only commandsdeploy and release carry disable-model-invocation: trueNo

      Hooks and permission rules steer an agent; they are not a security boundary. Keep org permissions, branch protection and CI in place.

      Known limitations

      • Not yet run end to end against a real org or Jira project. Prove deploy, test-run and Jira paths in a sandbox first.
      • No behavioural evaluation suite yet; agent quality is unmeasured.
      • Monitors and themes are experimental in Claude Code; monitors do not run in headless sessions.
      • No Salesforce MCP server: all Salesforce work goes through the sf CLI.
      • Source checks are heuristics; the Code Analyzer is the authoritative scan.

      The full list is in the README.

      Maintaining the kit

      Edit .claude/, never the generated folders in plugins/sf-sdlc/. Then regenerate and check:

      python3 scripts/build-claude-plugin.py          # regenerate the plugin and the skill catalog
python3 scripts/build-claude-plugin.py --check  # fail if anything generated is stale
node --test tests/kit.test.js                   # hook and CLI unit tests
claude plugin validate plugins/sf-sdlc --strict

      Bump version in plugins/sf-sdlc/.claude-plugin/plugin.json on every release, or installed copies will not update.
